引入 TTL：解决线程池中无法传递 ThreadLocal 的问题

发表于2025-12-15|更新于2025-12-15|Java技术
|浏览量:

问题背景

在 Web 应用中，认证 Token 的传递是一个常见需求。通常的做法是在过滤器（Filter）中解析请求头获取 Token，然后将用户标识存入 ThreadLocal 中，供后续业务代码直接获取。这种方式在同步调用链中工作良好，但一旦涉及异步处理或线程池，就会出现上下文丢失的问题。

以下是一个典型场景的简化代码：

在 Token 过滤器中，通过 ThreadLocal 存储认证信息：

public static final ThreadLocal<String> TOKEN_THREAD_LOCAL = new ThreadLocal<>();

@Override
public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    try {
        String token = httpRequest.getHeader("Authorization");
        // 省略校验逻辑 ...
        TOKEN_THREAD_LOCAL.set(result);  // 将 token 存入 ThreadLocal
        chain.doFilter(request, response);
    } finally {
        TOKEN_THREAD_LOCAL.remove();
    }
}

在业务层，可以直接通过 ThreadLocal 获取当前用户标识：

public class UserService {
    public void doSomething() {
        String userId = TokenFilter.TOKEN_THREAD_LOCAL.get();  // 直接获取
        // 业务逻辑 ...
    }
}

然而，当业务代码在异步线程或线程池中执行时，问题就出现了。

问题分析

考虑这样一种业务场景：订单创建接口需要在异步线程中执行库存扣减操作。

线程池配置如下：

@Bean
public ThreadPoolExecutor newBuyConsumePool(MeterRegistry registry) {
    ThreadPoolExecutor executor = new ThreadPoolExecutor(
            20, 32, 60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>());
    ExecutorServiceMetrics.monitor(registry, executor, "newBuyConsumePool");
    return executor;
}

在订单服务中，调用这个线程池执行异步任务：

@Autowired
private ThreadPoolExecutor newBuyConsumePool;

public void asyncProcess() {
    // 主线程中，ThreadLocal 可以正常获取
    String token = TOKEN_THREAD_LOCAL.get();
    System.out.println("主线程获取: " + token);

    // 提交到线程池执行
    newBuyConsumePool.submit(() -> {
        // 异步线程中，ThreadLocal 为 null
        String tokenInAsync = TOKEN_THREAD_LOCAL.get();
        System.out.println("异步线程获取: " + tokenInAsync);  // 输出 null
    });
}

输出结果：

主线程获取: abc123
异步线程获取: null

根本原因：ThreadLocal 的数据存储在当前线程的变量表中。当任务被提交到线程池时，虽然是同一个 Runnable 对象，但它会在不同的线程中执行。不同的线程拥有独立的变量表，因此无法访问主线程中设置的 ThreadLocal 值。

有些人可能会想到用 InheritableThreadLocal 替代。顾名思义，InheritableThreadLocal 允许子线程继承父线程的值。但它只适用于通过 new Thread() 创建线程的场景，无法跨线程池传递——因为线程池中的线程是预先创建并复用的，不会为每个任务创建新线程。

解决方案：TransmittableThreadLocal

阿里开源的 TransmittableThreadLocal（简称 TTL）专门解决了这个问题。它的核心原理是在任务提交到线程池时，主动将当前线程的 ThreadLocal 值复制到任务中，然后在异步线程执行时，再将这些值恢复到新线程的变量表中。

引入依赖

<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>transmittable-thread-local</artifactId>
    <version>2.14.3</version>
</dependency>

改造 ThreadLocal

将原来 ThreadLocal 的定义替换为 TransmittableThreadLocal：

import com.alibaba.ttl.TtlCallable;
import com.alibaba.ttl.TtlRunnable;

// 改造前
public static final ThreadLocal<String> TOKEN_THREAD_LOCAL = new ThreadLocal<>();

// 改造后
public static final TransmittableThreadLocal<String> TOKEN_THREAD_LOCAL = new TransmittableThreadLocal<>();

包装线程池

TTL 提供了多种方式让线程池支持上下文传递，推荐使用 TtlExecutors 包装：

import com.alibaba.ttl.threadpool.TtlExecutors;

@Bean
public ThreadPoolExecutor newBuyConsumePool(MeterRegistry registry) {
    ThreadPoolExecutor executor = new ThreadPoolExecutor(
            20, 32, 60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>());

    // 使用 TTL 包装，返回的线程池自动支持上下文传递
    return TtlExecutors.getTtlExecutorService(executor);
}

使用 TtlRunnable 或 TtlCallable 包装任务

如果不方便改造线程池定义，也可以在提交任务时手动包装：

// 手动包装 Runnable
Runnable ttlRunnable = TtlRunnable.get(() -> {
    String token = TOKEN_THREAD_LOCAL.get();  // 现在可以正常获取了
    // 业务逻辑 ...
});
newBuyConsumePool.submit(ttlRunnable);

// 或者包装 Callable
Callable<T> ttlCallable = TtlCallable.get(callable);
Future<T> future = newBuyConsumePool.submit(ttlCallable);

验证效果

改造后，同一个示例的执行结果：

主线程获取: abc123
异步线程获取: abc123

异步线程成功获取到了主线程设置的上下文信息。

总结

ThreadLocal 是 Java 中用于在同一线程内传递上下文数据的便捷工具，但它天然不具备跨线程传递的能力。在使用线程池进行异步处理时，必须借助 TransmittableThreadLocal 来实现上下文的完整传递。

关键改造点：

  1. 将 ThreadLocal 替换为 TransmittableThreadLocal
  2. 使用 TtlExecutors.getTtlExecutorService() 包装线程池，或在提交任务时用 TtlRunnable / TtlCallable 包装

这样，就能在异步场景下保持上下文的一致性，避免因线程切换导致的数据丢失问题。
